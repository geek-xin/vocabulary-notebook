# 联网补全成功后才呈现卡片 — 设计

**日期**：2026-10-02
**状态**：已与用户确认，待实现

## 1. 背景

当前实现（`index.html`）的导入路径是「解析 → 建空卡 → 落盘 → 立即 `renderHome()` 出真实卡片 → 800ms 后后台静默联网补全」。
后果：用户导入后立刻看到一堆释义为 `—` 的空卡，需要等后台补全把它们逐张填上。

用户要求：**联网导入成功后，才能呈现卡片。**

## 2. 目标

- 导入的新词汇本，在联网补全完成前不以真实卡片形态出现。
- 补全期间用户能看到明确的进行中状态与进度。
- 补全失败（离线 / 接口全挂）时不静默、不丢数据，用户可选择重试或仍然查看空卡。

## 3. 非目标

- 不改变启动回填（`backfillMissingWords`）与旧词汇本的行为。
- 不改变学习页（`studyView`）的呈现条件。
- 不引入新的持久化字段来记住「未完成」状态。

## 4. 关键设计决策

### 4.1 pending 状态只存在于内存

`book.pendingEnrich = true` 是**内存态，不写入存储**。

理由：若持久化，离线用户重开应用会永远看不到自己已经导入并落盘的数据，属于数据可用性事故。
页面重开后，该词汇本被视为已知词汇本，走原有的启动回填路径，正常显示。

数据安全：词汇本在导入解析完成后**立即落盘**，骨架卡只是同一个 `book` 对象的临时呈现形态，不存在丢数据窗口。

### 4.2 流程

1. 解析文件 → 建 `book`（带 `pendingEnrich`）→ `saveBooks(pending)` 落盘。
2. `renderHome()`：新词汇本渲染为**骨架卡**，旧词汇本照常渲染。
3. 立即启动 `enrichBooks(added)`（取消原 800ms 延迟）。
4. `enrichWords` 的 `onProgress` 不再弹 toast（原实现每 700ms 一次），改为驱动骨架卡进度文案。
5. 结束：清除 `pendingEnrich` → `saveBooks` → `renderHome()` 换成真实卡片 → toast 汇报结果。

### 4.3 成功 / 失败判定

`enrichWords` 需要新增返回字段 `answered`：本次至少有一次词典来源正常应答（HTTP 层成功），
区别于 `filled`（真的填进了内容）与 `remaining`（仍缺释义的词数）。

| 场景 | 判定 | 呈现 |
| --- | --- | --- |
| 联网开关关闭 / `navigator.onLine === false` | 失败 | 骨架卡失败态 |
| 有网络但零应答且零填充 | 失败 | 骨架卡失败态 |
| 有应答，部分词条查不到 | **成功** | 真实卡片，缺的保持空卡 |
| 全部补全 | 成功 | 真实卡片 |

「部分词条查不到」不算失败：个别生僻词不应把整本词汇本永久卡住。

### 4.4 失败态 UI

骨架卡显示「联网补全失败」+ 两个按钮：

- **重试**：重新对这本跑 `enrichBooks`，回到进行中态。
- **仍然查看**：清除 `pendingEnrich`，渲染为空卡（用户主动接受）。

同时 toast 明确提示「未能联网补全，词汇本已保存」，不静默失败。

### 4.5 骨架卡交互

- **不可点击**进入学习页：避免点进去全是空卡。
- **隐藏分享**：导出内容会是空释义，无意义。
- **保留删除**：允许用户撤销本次导入。
- 样式沿用 `.book-card`，新增 `.book-card.is-pending` 变体，深色 / 浅色主题都要覆盖。

## 6. 验证

- `npm test`（内联 JS 语法检查 + sw 测试）必须通过。
- Playwright 实测三条路径：
  1. 正常联网导入 → 先骨架卡 + 进度，后真实卡片，释义完整。
  2. 断网导入 → 失败态 + 「仍然查看」可放行。
  3. 部分词条查不到 → 成功态 + 少量空卡。

## 7. 风险

- 导入大词表（数百词）时，补全耗时可能数十秒，用户等待期间骨架卡必须给出明确进度，否则体感像卡死。
- `answered` 的判定依赖两个上游接口（有道 / Datamuse）的 HTTP 状态，需要确认现有 `lookupOnline` 的 `ok` 语义可用。
